# roadmap 使用指南

[English](GUIDE.md) | 简体中文

什么时候用 roadmap、怎样划分工作，以及一次典型的使用过程。命令和限制见 [README](README.zh.md)。

## 用途

Roadmap 把仓库的目标和交付记录保存在 `docs/roadmap/` 中，由代理维护。它回答单个计划回答不了的问题：为什么做、这一轮承诺了什么、哪些已经证明、哪些还欠着。新会话读一遍就能接着做，不用你再介绍项目。

| 组件 | 负责 |
| --- | --- |
| Roadmap | 目标、阶段、依赖、完成标准、延后的工作、结果。 |
| Prometheus | 一件工作怎么做：计划。 |
| Atlas | 执行已批准的计划并收集证据。 |

Prometheus 和 Atlas 来自 `omo-prometheus`；没有它 roadmap 也能用，但下文与计划相关的功能需要它。Roadmap 从不保存计划，需要展示时才读取 Atlas 计划包。

它需要本地 Git 仓库，但不需要远程仓库或托管服务。关闭阶段时只检查每条标准是否有证据，不检查证据是否属实。已关闭的阶段和轮次会被冻结，计划完成也不会自动关闭阶段。

## 什么时候用

当工作需要在多次执行之间保留目标、顺序、决策和未了结的事项时使用：

| 场景 | 用法 |
| --- | --- |
| 大型新项目 | 第一轮的阶段写详细，后面的轮次保持粗略。 |
| 迁移或替换系统 | 兼容和回滚各自成为阶段；把"旧路径已移除"写进最后一个阶段的标准。 |
| 长期产品迭代 | 每轮一个产品目标；延后的想法记成 TODO，指向后面的阶段或触发条件。 |
| 技术债或性能优化 | 先做基线阶段；之后的阶段写可度量的标准和停止条件。 |
| 安全或审计整改 | 每个发现或每类发现一条标准；接受的风险连同原因记录。 |
| 先调研再开发 | 调研阶段的结果是一份关联到该阶段的 ADR；实现阶段依赖它。 |
| 接手或恢复项目 | 以今天的代码为基线初始化，不补写历史。 |

一个会话能做完的修复、一次性实验、繁忙的分诊队列，以及跨多个仓库的协调（每个 Git 根目录只有一份路线图、一个活动轮次），都不适合。路线图之外的工作不需要阶段，代理可以把它记为自由工作。

## 轮次、阶段和计划

**轮次**有一个结束时能判断成败的目标，例如"首批用户能完成核心流程"。同一时间只有一个活动轮次。关闭时记录目标是 `achieved`、`partial`、`not_achieved` 还是 `cancelled`。

**阶段**是可以单独验证的结果，例如"用户能登录并看到自己的数据"，带两到六条完成标准。不要按层次切分（后端、前端、测试），因为其中任何一部分单独都无法判断是否完成。只有真正的前置条件才声明为依赖。

**计划**覆盖阶段的部分或全部标准，一个阶段可以有多个计划。每个计划声明自己负责的标准：

```text
Roadmap criteria: DC1, DC3
```

Prometheus 会在你批准计划之前检查这一行。如果一开始就知道阶段包含几块庞大且独立的内容，就拆分阶段。

经验值：每轮三到八个阶段。五到八个计划用一轮就够；更多时，保留一个活动轮次、一个写详细的计划中轮次，之后的轮次保持粗略。

## 示例

替换认证系统大约需要六个计划，因此分两轮：

- R1"证明新系统可用"：S01 记录现有登录路径，S02 新登录路径端到端可用，S03 完成回滚演练。
- R2"安全切换"：S04 身份映射，S05 小范围切换，S06 全量切换并移除旧路径。

做 S02 时，代理发现密码重置的行为不同，于是记下一条指向 S05 的 TODO。R1 关闭时，这条 TODO 以相同 ID 移入 R2，并出现在 S05 的交接内容里。S02 本身可能需要两个计划，一个声明 `DC1`，另一个声明 `DC2, DC3`；每条标准都有通过的证据后即可关闭。

## 典型流程

1. 运行 `/init-project` 并确认预览。用 `/roadmap plan-round` 起草后面的轮次。
2. 问代理哪些阶段可以开始。代理能看到哪些已就绪、哪些在等依赖。
3. 开始阶段，然后用 `/prometheus` 做计划，顺序反过来也可以。交接内容包括本轮的目标、约束和非目标，前置阶段交付了什么，未关闭的 TODO、ADR，以及该阶段已有的计划。在规划中开始阶段只会绑定，阶段保持计划状态；Atlas 会在派发第一个任务前开始它并提交。
4. 工作中，范围变化记为阶段修订，以后再做的事记为 TODO，决策记为 ADR。计划批准后如果阶段发生变化，会收到提示，执行不会暂停。
5. Atlas 释放计划之前，每个范围外的发现都会被归为 TODO、重复或不处理，并列在最终报告里。
6. 计划完成后，提醒会显示所有计划对标准的覆盖情况。每条标准都有通过的证据后关闭阶段。
7. 所有阶段关闭或放弃后，运行 `/roadmap close-round`，记录目标结果，再决定下一轮。

可以这样问：

- "现在哪些阶段可以开始？推荐下一个，先别做计划。"
- "开始 S04，先检查本轮约束和前面阶段交付了什么。"
- "这个计划做完了，S04 能关闭吗？列出还没证明的部分。"
- "关闭本轮之前，告诉我目标有没有达成。"

轮次级别的变更始终需要你运行命令并确认预览。

## 仓库格式 2

计划中的轮次、目标日期和轮次目标结果需要仓库格式 2。`/init-project` 创建的就是格式 2 的仓库，共用它的人需要使用比 0.2.3 更新的 roadmap 版本。由更早版本初始化的仓库是格式 1：会话开始时 roadmap 会询问是否升级，选"否"不会改动任何内容。也可以运行 `/roadmap upgrade`。升级后，**roadmap 0.2.3 及更早版本将无法读取该仓库**，所以请先让共用仓库的人更新插件。
