# judge-dispatch 参考

## 代理发现

候选代理来自实时 `task` 工具描述中的代理列表。列表缺失、无法解析或为空时，插件不做判断。插件写入的任何代理名都会再经过 `task` 工具校验。是否只读取决于 OMP 的代理工具元数据。

只要评级能改变某些东西，即使只有一种代理类型可选，judge 也会评估难度：开启了 `judgeEffort` 且条目没有设置 `effort`，或者 `modelTiers` 中有条目适用于最终使用的代理。如果只有部分候选代理配置了档位，插件会先选择代理，仅在选定代理有档位时才询问难度。被固定的条目永远不会被询问难度。

## 模型档位

`modelTiers` 是以逗号分隔的 `[<agent>.]<routine|demanding>=<selector>` 条目列表。任何格式错误或重复的条目，以及 `standard` 条目，都会使整个设置无效，此时插件原样保留所有调用。对于任务最终使用的代理，插件先查找 `<agent>.<difficulty>`，再查找 `<difficulty>`。

档位的展开方式与固定完全相同：

- `@<role>`：展开后的 `modelRoles[role]` 选择器，后接 `retry.fallbackChains[role]`；角色没有配置链时后接 `default` 链。
- `provider/model[:level]`：该选择器，后接 `default` 链。

在 `tool_call` 阶段，插件根据当前项目的 OMP 设置和已启用模型检查档位：角色必须存在，回退链必须是不含提供商通配符的选择器列表，并且必须有已启用的模型能够解析。未通过检查的档位会保留代理的模型，并在状态行中写明原因。只有当档位第一个解析成功的模型就是代理自身选择器解析到的模型，并且思考级别也相同（选择器显式的 `:level`，没有时使用代理的 `thinkingLevel`）时，档位才不做任何改变，此时思考级别调整仍可能生效。档位指定代理自身模型但级别不同时，会应用该级别，不再做思考级别调整。与固定不同，只解析出一个选择器、自身没有回退链的档位不会被拒绝；OMP 会用代理自己角色的链重试它，即回退到代理的模型一侧。

## 思考级别调整

OMP 按以下顺序决定子代理的思考级别：任务的 `effort`，然后是模型所解析的选择器上显式的 `:level` 后缀，最后是代理定义的 `thinkingLevel`。`effort`（`lo`、`med`、`hi`）会映射到模型支持的最低、中间或最高级别，所以写入它会抹平精心配置的级别，例如代理的 `xhigh`。插件从不写入 `effort`。

开启 `judgeEffort` 且条目没有 `effort` 时，插件按以下步骤计算调整：

1. 基准是 OMP 在没有 `effort` 时会使用的级别：第一个能解析到已启用模型的选择器上的 `:level`，没有时使用代理的 `thinkingLevel`。没有基准，或者基准为 `auto`、`inherit`、`off` 时不做调整。
2. 基准先按模型支持的级别收敛，与 OMP 应用级别时的做法一致。
3. routine 评级下调一个受支持的级别，demanding 评级上调一个受支持的级别。最低受支持级别之下、最高受支持级别之上都不再调整，所以调整永远不会降到 `off`。
4. 结果再按 `task.maxEffort` 收敛。OMP 只对 `effort` 应用这个上限，所以插件自己应用它。会被上限抵消的上调直接放弃。

级别的顺序和受支持的级别来自 OMP 自身的思考级别工具函数和模型注册表。派生时，插件为解析成功的那个选择器添加或替换 `:level` 后缀，选择器本身和其他模式都保持不变。OMP 把这个后缀视为显式指定，所以它优先于代理的 `thinkingLevel`。档位切换了模型时，不做思考级别调整。

## 重试与升级记录

插件会告诉父代理：要重试或升级某个任务，就用同一个 `name` 再派发一次。它在每个会话中按调用方写下的原始任务名称保存记录，所以 `Lane-1` 和 `Lane-2` 互不影响。子代理通过它在被路由调用中的条目位置对应到名称，而不是去掉 OMP 在名称冲突时为子代理 ID 追加的 `-N` 后缀：

- 升级：子代理最终输出的第一个非空行恰好是 `ESCALATE: deep-high`。下一次派发按 `demanding` 处理。
- 失败：子代理在派生时应用了 routine 档位或思考级别下调，之后以中止、非零退出码或错误结束。下一次派发比当时应用的难度高一级。

插件不使用 `tool_result` 钩子读取结果。同步子代理的结果包含在该 `task` 调用 `tool_execution_end` 事件的 details 中。对于后台子代理，该事件会按子代理 ID 和派发时间绑定父会话中的异步任务；任务结束时，由它的状态判断是否失败，子代理输出则从任务交付的 `<task-result>` 文本的 `<output>` 或 `<preview>` 块中读取。只有插件路由过的调用才计入，所以已批准的 Prometheus 计划执行期间不会记录任何内容。工作流专属代理的子代理和固定派生名称永远不会被记录。

下一个被路由的同名任务条目会使用这条记录。它保留请求的代理，跳过 judge，并照常通过档位和思考级别调整作用于记录的难度；该条目若有固定，仍以固定为准。只有当提升后的路由真正被返回时，记录才会被删除；保留原路由的条目（工作流专属或未列出的代理），以及路由超时或失败放行的调用，都会把记录留给下一次派发。每类记录最多保存 256 条，最早的先被淘汰。

## 从判断到派生

OMP 的 `before_subagent_spawn` 事件不携带任务内容，所以插件通过任务项的 `name` 把档位或思考级别调整和派生关联起来。父代理没有给名字时，插件会写入一个（`<agent>-<8 hex>`）。如果两个待处理调用同名，这次派生就保留原先配置的模型。派生时，第一个解析成功的选择器必须仍是做出判断时的那个模型，思考级别调整会重新计算，只有落到同一级别时才生效；否则派生保留原有配置。这一步出现任何失败都保留原先配置的模型。OMP 会在子代理解析出的模型旁显示路由说明。

改写只会改动：开启 `routeAgent` 或条目固定了模型时的 `agent`，以及档位、思考级别调整或固定需要时的 `name`。

## 从固定代理到派生

task 模式没有逐条目的模型字段，严格工具模式也不允许模型自行添加字段，所以固定标记写在 `agent` 字符串里：`@` 之后不含 `/` 时为 `<agent>@<role>`，否则为 `<agent>@<provider>/<model>`。在 `tool_call` 阶段、judge 判断之前，插件根据当前项目的 OMP 设置和已启用模型校验调用中的每个固定。随后把每个固定条目的 `agent` 改回原代理名，把 `name` 改为唯一的 `<name 或 agent>_jd<12 hex>` 派生名称，并以此关联固定的模型选择器。只要有一个固定无效，整次调用都会被拒绝；名称已带这种 `_jd` 形式的未固定条目也会被拒绝，因此这类派生名称一定代表固定。固定条目不会被询问难度，也不使用档位或思考级别调整，代理判断照常进行；之后即使路由失败，也仍返回固定后的改写。OMP 会显示并保存改写后的调用，所以结果还带有 `additionalContext`，告诉父代理哪个条目改用了哪个派生名称和模型；否则父代理读到自己的调用时会把改写当成错误而重新派发。`before_subagent_spawn` 按派生名称找到固定并替换模型选择器。注册表属于插件实例，所以会话切换后才启动的后台任务仍能找到自己的固定。没有留下后台任务就结束的调用会丢弃未使用的固定。等待中的固定超过 256 个时会淘汰最早的；若某次派生的固定名称已找不到对应固定，会拒绝派生，而不是用代理自己的模型启动。

固定角色时，插件提交展开后的 `modelRoles[role]` 选择器，后接 `retry.fallbackChains[role]`；角色没有配置链时后接 `default` 链。固定具体模型时，提交该选择器，后接 `default` 链。插件不会在这些回退模型中主动选择。OMP 会保留代理原有的 `modelRole`，并用该角色的链（或 `default`）重试只有一个选择器的模型，因此当固定只解析出一个选择器、而继承的链非空时，派生会被拒绝，避免借用错误的链。该钩子无法改变已保存的角色身份或 OMP 的凭据回退；已停放子代理冷恢复时也可能重新解析代理自己的角色。

## 超时与失败

路由最多等待八秒，并且总会在会话工具调用处理超时前至少一秒结束；如果已经没有时间，就跳过路由。请求、凭据和用量记录都经由 OMP 的 `judge` 角色处理；插件不保存密钥，也不改动进程环境变量。

## 状态

插件不在会话文件中保存路由状态，也不发布插件状态快照。待应用的档位和思考级别调整、模型固定，以及重试与升级记录都只保存在当前进程中；重启后丢失。清单中已不再声明的已存设置会被忽略，并在每个会话中警告一次，提示改用 `modelTiers`。旧版本的对话记录仍可正常渲染和过滤。
